## Bagian 3 — Debug "icon unclickable" (bukan bug kode)

User laporkan ikon baru "tidak berfungsi alias unclickable" begitu
dicoba, minta jalankan test. `npm test` tetap hijau (gak nangkep ini —
gak ada unit test buat interaksi UI/route baru). Investigasi lanjut pakai
browser Chrome MCP:

1. Login `demo-tab` (kredensial demo lokal sintetis, `auth/src/credentials.seed.json`),
   buka Summary Progress All Dinas — ikon KELIHATAN dan KE-KLIK (state
   `--active` berubah), tapi panel breakdown nunjukin error:
   `Http failure response for .../TB/breakdown: 404 Not Found`.
2. Curl langsung ke backend (port 4000, dan lewat proxy 4200) TANPA token
   balik 401 `"X-Session-Token or X-User-Id header required"` — sempat
   disalahartikan sebagai "route ada, cuma butuh auth". **Salah** — root
   cause sebenarnya: `router.use(requireUser)` di `dashboard.js` jalan
   untuk SEMUA path di bawah `/api/dashboard/*` SEBELUM Express sempat
   coba cocokkan route spesifik, jadi 401 muncul bahkan untuk path yang
   sama sekali gak terdaftar — false positive.
3. Login ke `auth` service langsung via curl buat dapat token TAB asli,
   replay request `/breakdown` dengan token itu → hasilnya BENERAN 404
   Express native (`Cannot GET /api/dashboard/summary/TB/breakdown`,
   bukan JSON `{ok:false}`) — baru ketauan endpoint-nya emang gak
   terdaftar di proses yang lagi jalan.
4. `netstat` + `Get-CimInstance Win32_Process` nunjukin proses backend di
   port 4000 (PID 12132, `node src/index.js`, start jam 14:16) sudah
   jalan SEBELUM edit `dashboard.js` — Node gak ada hot-reload buat
   `src/index.js` (bukan `nodemon`), jadi proses lama masih pakai kode
   lama walau file di disk sudah berubah.
5. Fix: kill PID 12132, `npm start` ulang. Verifikasi curl (`ok:true`,
   6 pasangan breakdown TB muncul) dan verifikasi live di browser — panel
   breakdown muncul dengan card per pasangan (TB→Corp, TB→TC, dst,
   masing-masing progress bar sendiri), klik satu kartu berhasil navigate
   ke `/rdt/dashboard/detail/TB/Corp` (halaman existing, render normal
   dengan thread diskusi).

**Bukan bug kode fitur** — murni proses dev backend yang lupa di-restart
setelah edit source. Dicatat sebagai catatan operasional buat sesi depan:
backend `rdt/backend` gak punya watch/hot-reload, restart manual tiap ada
perubahan source saat `npm start` sedang jalan di background.

## Bagian 4 — Fix gap `DashboardDetailComponent.submitComment()` (temuan sesi 8, ditunda)

Sesi 8 nemu (lewat trace `/graphify`) `submitComment()`
(`dashboard-detail.component.ts:200`) masih pakai pola load()-error
(`this.errorMessage = extractErrorMessage(...)`, banner inline di TOP
halaman) padahal ini aksi mutating (POST comment) — beda dari pola semua
aksi mutating lain di app yang pakai `ModalService.alert()` biar error
kelihatan di manapun posisi scroll user (kotak komentar sendiri ada di
BAWAH halaman, jauh dari banner). Waktu itu ditunda user buat didiskusikan
dulu.

Sesi ini user konfirmasi temuan itu valid, minta diperbaiki, dengan satu
arahan eksplisit: **jangan asumsikan sendiri pola "modal saja" vs "modal +
banner"** — cek dulu persis 2-3 dari 20 pemanggil mutating yang sudah
benar, baru samakan persis. Dicek `confirm.component.ts` (resolveBorne/
resolveReassign), `share-cost.component.ts` (splitRow),
`repost-history.component.ts` (addSubdoc) — semua pola identik:
```ts
error: async (err) => { <reset busy flag>; await this.modal.alert('<prefix>: ' + extractErrorMessage(err, String(err))); }
```
tanpa banner tambahan. `submitComment()` disamakan persis ke pola itu:
inject `ModalService`, error handler jadi `async`, panggil
`this.modal.alert('Gagal mengirim komentar: ' + extractErrorMessage(err, String(err)))`,
hapus write ke `errorMessage` di jalur itu (banner di `load()` gak
diapa-apain — itu memang pola GET-error yang benar).

`ng build` bersih, `npm test` tetap 82/82 (perubahan frontend-only).
Di-commit sebagai `4ca58be`.
