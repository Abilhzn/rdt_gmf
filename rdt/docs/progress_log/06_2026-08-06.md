## Arc A part 2 — REQ-RDT-SAP-14: deadline mechanism (the session's main feature)

Built across three rounds, each gated through Plan Mode
(`EnterPlanMode`/`ExitPlanMode`) with explicit user approval before execution,
per the user's standing "rencana dulu, baru eksekusi" instruction.

### Round 1 — per-pasangan deadlines, computed live

Initial design: TAB sets a confirmation deadline per `(dinas_inisiasi,
dinas_target, periode)` triple, binding the TARGET dinas's Confirm/Reject
action. Built:
- Migration `016_period_deadlines.sql` — new `rdt.period_deadlines` table.
- `rdt/backend/src/rules/periodEffective.js` — pure function
  `computeEffectivePeriod({declaredPeriod, deadlineAt, latestTargetActionAt})
  -> {periodeEfektif, overdue}` plus an `addMonths` helper.
- `rdt/backend/src/routes/periodDeadlines.js` — `GET /`, `POST /` for the
  per-pasangan CRUD, TAB-only (`requireRole('TAB')`).
- Frontend: per-pasangan deadline-setting form added to Riwayat Repost TAB.

Followed the pre-existing "computed, not stored" convention already used
elsewhere in `exportBatches.js` (the WAITING state, the old overdue flag) —
`GET /history` would call `computeEffectivePeriod` live on every read rather
than storing a result. This was explicitly flagged as my own default choice,
pending confirmation, not a locked decision.

### Round 2 — user override: snapshot, not live-computed

The user explicitly reversed the live-computed default:

> "Soal open question retroaktif — ubah jawabannya jadi: SNAPSHOT, bukan
> live-computed. Begitu dinas target melakukan Confirm/Reject, kunci
> periode_efektif SAAT ITU JUGA... simpan sebagai kolom permanen — BUKAN
> dihitung ulang tiap kali dibaca... kalau live-computed, TAB edit deadline
> bisa diam-diam mengubah status 'overdue'/periode transaksi yang sudah
> terjadi di masa lalu — itu bikin data finansial 'melayang' tergantung edit
> belakangan, susah diaudit."

This was accepted without pushback as a legitimate business-logic authority
correction. Rebuilt around a permanent snapshot:
- Migration `017_periode_efektif_snapshot.sql` — new `periode_efektif` column
  on `rdt.transactions`.
- `confirmation.js` — new `snapshotPeriodeEfektif(client, {transactionId,
  dinasInisiasi, dinasTarget, declaredPeriod})` helper, called once at the
  moment of CONFIRM and at DECLINE-without-redirect; the REJECT_REDIRECT
  branch instead nulls `periode_efektif` (no snapshot yet — the chain isn't
  resolved).
- `reassignment.js` — the REASSIGN branch's UPDATE also nulls
  `periode_efektif` for the same reason.
- `exportBatches.js`'s `GET /history` simplified to just read
  `MAX(periode_efektif)` per batch — no more live computation.
- `computeEffectivePeriod()` itself was untouched — only the CALLER and
  TIMING changed (read-time → write-time-once).

Verified live: an ad-hoc DB script proved that editing a deadline AFTER a
pasangan's Confirm/Reject action does NOT retroactively change that
pasangan's already-snapshotted `periode_efektif` — only future
Confirm/Reject actions see the new deadline.

Bug fixed along the way: a stray literal null byte (`0x00`) inside a template
literal in `exportBatches.js`'s `/waiting` route (should have been a plain
space) — invisible to the Edit tool's exact-string matching, found via
`buf.indexOf(0)` (offset 5429) and fixed with a raw Node.js Buffer
read/replace/write, confirmed gone via `cat -A`.

### Round 3 — user correction: deadline-setting is bulk, not per-pasangan

A second correction from the project owner (SRS.md's "DIKONFIRMASI 5 Agu,
malam" section):

> "cara set deadline itu ternyata BULK, bukan satu-satu... TAB set SATU
> deadline yang otomatis berlaku ke SEMUA pasangan aktif di periode itu
> sekaligus... Override per pasangan spesifik tetap ada sebagai
> pengecualian (tabel period_deadlines yang sudah ada TETAP DIPAKAI, jangan
> dibongkar)."

Per-row snapshot granularity (Round 2) was separately reconfirmed correct and
untouched — validated against a complex split+redirect+reconverge scenario.

Planned first (definition of "pasangan aktif di periode itu" was the key
design question, per the user's explicit request to see the query before
execution) and then built:
- `POST /api/period-deadlines/bulk` — body `{ periode, deadline_at }`, no
  specific pasangan. Upserts into the SAME `rdt.period_deadlines` table for
  every pasangan with at least one transaction in that periode still in a
  non-terminal state (`BLOCKING_STATUSES = ['PENDING', 'DECLINED',
  'NEEDS_REVIEW']`, the same constant `exportBatches.js` already used for its
  own readiness gate):
  ```sql
  INSERT INTO rdt.period_deadlines (dinas_inisiasi, dinas_target, periode, deadline_at, set_by_user_id)
  SELECT DISTINCT t.dinas_inisiasi, t.dinas_target, $1, $2::timestamptz, $3
  FROM rdt.transactions t JOIN rdt.uploads u ON u.id = t.upload_id
  WHERE u.period = $1 AND t.dinas_target IS NOT NULL AND t.status_konfirmasi = ANY($4)
  ON CONFLICT (dinas_inisiasi, dinas_target, periode)
  DO UPDATE SET deadline_at = EXCLUDED.deadline_at, set_by_user_id = EXCLUDED.set_by_user_id, updated_at = now()
  RETURNING *
  ```
  (Needed an explicit `$2::timestamptz` cast — without it Postgres can't
  infer the bind parameter's type from a `SELECT`-list position the way it
  can in a plain `INSERT ... VALUES`, and rejected it as text vs. the
  column's `timestamptz` type. Diagnosed by re-running the failing request
  via a raw `fetch()` one-liner since the test script's `report()` helper
  didn't log the response body on a bare 500.)
- Shared `validatePeriodAndDeadline()` helper factored out of the existing
  per-pasangan `POST /`, used by both routes.
- Frontend (`repost-history.component`): new "Set Deadline untuk Semua
  Dinas" sub-section added ABOVE the existing per-pasangan override form,
  inside the same `<details class="deadline-panel">` — explicitly NOT
  replacing the per-pasangan form, per the user's "JANGAN gantikan yang
  sudah ada". Own state (`bulkDeadlineForm`), gated behind
  `ModalService.confirm()` before submitting since it can touch many
  pasangan at once.
- `export-batch.service.ts` — new `setBulkPeriodDeadline(periode,
  deadlineAt)` method.

Verified live: DB script with 3 synthetic pasangan (2 PENDING, 1 already
CONFIRMED) confirmed bulk-set only touched the 2 active ones; browser
click-through as `demo-tab` on Riwayat Repost TAB confirmed both forms render
side by side, confirm dialog fires, and the success message lists affected
pasangan. `npm test` 75/75 green throughout all three rounds; `tsc --noEmit`
clean.
