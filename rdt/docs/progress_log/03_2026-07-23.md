- **Design fork surfaced to the user before coding**: `rdt.comments.transaction_id`

  (e.g. TC→TJ), not one transaction. Two options were presented:
  - **(A, recommended, chosen by user)** no schema change — new
    top-level comments auto-attach to the most-recently-created
    transaction between the pair; replies inherit their parent's
    `transaction_id`; reading the thread means joining comments across
    every transaction in the pair and merging by time.
  - (B) schema change — relax `transaction_id` to nullable and add
    `dinas_inisiasi`/`dinas_target` columns directly to `rdt.comments`.
- Built on Option A:
  - `sql/migrations/002_notifications.sql` — new `rdt.notifications`
    table, additive only.
  - `src/rules/mentionRules.js` — pure module parsing/resolving
    `@mentions` (`@username` or `@DINAS`, which fans out to every user in
    that dinas); `mentionRules.test.js` (9 tests), all green.
  - `dashboard.js` extended (with a refactor to share the existing
    chain-aware progress logic): `GET /api/dashboard/detail/:initiatorDinas/:targetDinas`

    `GET .../comments` (so posting doesn't require re-fetching everything),
    and `POST .../comments` (`{body, parent_comment_id?}` — replies
    inherit the parent's `transaction_id` server-side, never trusting
    client input for it).
  - `GET`/`POST /api/notifications` — mentions create notifications; a
    bell badge in the topbar shows the unread count; clicking marks read

  - Dashboard cards are now clickable (drill down to the pair) **except**

  - New "Dashboard-Detailing" page: progress donut, reply count, indented

## Decisions / notes worth remembering
- Pivot/summary sheet detection is an **OR**: name contains
  "summary"/"Summary" (case-insensitive) OR cell `A3` = "Sum of In PCLC".
- Downloaded original files are **intentionally unfiltered** (contain all
  dinas in the upload) — required for live formulas to resolve; never
  "fix" this into a per-dinas filtered export without asking first.
- Credentials for login are synthetic/demo and stored separately from the
  public employee directory specifically to avoid leaking through
  `GET /api/directory`.
- Standing workflow change (23 Jul): new features go backend +
  `ui-demo.html` first, then get ported to Angular as a **separate** later
  step — not built in parallel across both frontends anymore.
- Dashboard-Detailing comments deliberately reuse existing
  `transaction_id`-anchored schema (Option A) rather than changing it —
  comments on a dinas pair attach to that pair's most recent transaction;
  replies always inherit the parent's transaction, never client-supplied.
- Unmapped/ambiguous dinas codes (e.g. `TJ-TMM`'s `ZGMFTMM`) and rows with
  no usable `Remarks` both now correctly land in `NEEDS_REVIEW` rather
  than being silently dropped or silently stuck with no dinas target.
