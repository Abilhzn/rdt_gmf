## Bagian 3 — Data engineering / ODS: index `dinas_inisiasi`

User reframe: karena app ini ODS (Operational Data Store), minta index
& bentuk database dicek ulang dari sudut data engineering. Baca
`schema.sql` + seluruh 18 file `sql/migrations/` + call-site query
sungguhan. Temuan konkret satu: `schema.sql` sudah punya
`idx_txn_target_status (dinas_target, status_konfirmasi)` untuk sisi
"confirm" pasangan, tapi tidak ada pasangannya untuk sisi "inisiasi" —
padahal pola akses inti tabel ini per-pasangan
`(dinas_inisiasi, dinas_target)`, bukan per-target saja. Query yang kena
(`dashboard.js` NEEDS_INVESTIGATION/actionable counts, `reassignment.js`
pending-count, keduanya filter `dinas_inisiasi + status_konfirmasi`) jatuh
ke sequential scan tanpa index ini — dan `rdt.transactions` adalah satu-
satunya tabel yang benar tumbuh tiap bulan (volume transaksi nyata),
beda dari `export_batches`/`comments`/`notifications` yang tetap kecil.

Dibuat `sql/migrations/019_txn_inisiasi_status_index.sql`:
```sql
CREATE INDEX IF NOT EXISTS idx_txn_inisiasi_status
  ON rdt.transactions (dinas_inisiasi, status_konfirmasi);
```
Mirror persis bentuk index yang sudah ada, idempotent (`IF NOT EXISTS`),
sesuai konvensi `sql/migrations/` (`schema.sql` tidak diedit retroaktif).
Diputuskan eksplisit **TIDAK** menambah index di `export_batches`/
`comments`/`notifications` (tabel kecil, bounded) dan **TIDAK**
merenormalisasi bentuk 53-kolom-flat `transactions` — dijelaskan alasannya
ke user, bukan cuma di-skip diam-diam.
