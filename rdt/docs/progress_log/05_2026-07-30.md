## The architectural pivot: per-dinas_inisiasi → per-pasangan

**What was wrong and why:** the previous model grouped/gated Need Approval work by `dinas_inisiasi` alone, so one slow-to-confirm target dinas blocked TAB from processing an initiator's other, already-ready pairs. The TAB team corrected this in person: the gate must be scoped to the individual `(dinas_inisiasi, dinas_target)` pair.

**What carried over vs. what was rebuilt:** the assistant reported that the comment/notification fan-out logic, the transparency-before-confirm pattern, the mandatory-closing-description gate, the 53-column SAP export, and the audit-log shape were all sound and reusable — only the *grouping key and gate scope* needed to change from `dinas_inisiasi` to `(dinas_inisiasi, dinas_target)`. As a side effect, the per-pair model actually simplified the comment/notification code (one pair → one comment, no loop over multiple targets).

Nothing had been committed yet at the point of correction, so nothing needed git-level rollback — only working-tree code needed rewriting.

## Tahap 1 — per-pasangan rework (executed after user confirmation)

- **`rdt/backend/sql/migrations/007_export_batches_per_pasangan.sql`** (new): adds `dinas_target NOT NULL` to `rdt.export_batches`, wipes the 4 old per-dinas_inisiasi test rows (confirmed via a direct DB check that 0 transactions were linked to them, so safe to discard).
- **`rdt/backend/src/routes/exportBatches.js`** (rewritten): `GET /waiting` now groups by `(dinas_inisiasi, dinas_target)` pair, not just initiator; `POST /confirm` takes a pair and posts one comment/notification (no more per-target loop); `GET /export-pairs` (the old per-pair picker, no longer needed) removed; `GET /export/:batchId` no longer takes a target parameter.
- **Angular** (`export-batch.service.ts`, `need-approval.component.ts/html/scss`): queue keyed by pair, Confirm button and confirmation dialog scoped per pair ("Confirm repost TC → TN"), direct download with no picker since a batch is now unambiguous.
- **Verification**: `npm test` 47/47 green; live browser walkthrough as `demo-tab` with seeded data `TB→TM` (2 CONFIRMED, ready) and `TB→TE` (1 PENDING, deliberately left unresolved) proved the core fix — `TB→TE` being PENDING did **not** block `TB→TM` from appearing in the queue. A fresh pair `TC→TN` was confirmed end-to-end through the UI with no console errors.

## Post-commit code review — 4 gaps fixed (REQ-RDT-COMMENT-04, SAP-11, SAP-12, + notification gap)

The user did a hands-on review of the actual code (not just the summary) and reported the per-pasangan model, chain-aware progress (`fetchReassignChainMap`, correctly handling `TJ→TE→TL` redirect chains), and the TMM/TM separation were all solid and untouched. Four concrete gaps were flagged and fixed in parallel (independent):

1. **REQ-RDT-COMMENT-04** — `mentionRules.js`: the mention token `"TA"` (case-insensitive) is now aliased to resolve to dinas `"TAB"` instead of being looked up as a nonexistent `dinas_code="TA"`. Test case added to the existing mention-rules test suite.
2. **REQ-RDT-SAP-11 (subdoc-to-transaction linkage)** — new migration 009 (`009_subdoc_transaction_linkage.sql`) adds a `subdoc_id` column on `rdt.transactions` (chosen over a junction table as more consistent with the existing pattern, e.g. `export_batch_id`). `POST /:batchId/subdocs` now accepts an optional `transaction_ids` list, defaulting to all of the batch's not-yet-assigned transactions when omitted. New `GET /:batchId/lines` endpoint and enriched `GET /history` expose the linkage. Verified end-to-end via curl with seeded data.
3. **REQ-RDT-SAP-12 (CBO visibility)** — the initiating dinas's PIC needed to see their own repost status/subdocs without TAB-only gating. Implemented by adding `state_label` to `buildChainAwareProgress`'s `as_initiator` view in `dashboard.js`, correctly unioning subdoc numbers across every batch a card's redirected transactions ended up in (handles the chain-key-mismatch edge case). A first draft added a separate new endpoint, but a same-session follow-up correction from the user (see "Item 5" below) had it consolidated onto the existing `GET /history` endpoint instead, and the extra endpoint was removed.
4. **Confirmation description not notifying anyone** — `confirmation.js`'s optional closing description (the `trimmedDescription` block on submit) was posting a comment but not triggering any notification, unlike regular comments which go through `resolveMentionedUserIds`. Fixed to notify the `dinas_inisiasi`'s PIC(s) using the same fan-out pattern as `exportBatches.js`'s closing description. Verified live via curl: `demo-tj` (PIC of the initiating dinas) received the notification.

**Item 5 (user follow-up, expanding SAP-12's scope)**: rather than a separate TAB-only endpoint plus a separate PIC-only endpoint, the user asked to consolidate onto a single `GET /export-batches/history` — `requireRole('TAB')` was moved off the router-level `router.use` and onto individual routes instead, and `/history` now auto-scopes: TAB sees all dinas, a non-TAB caller is automatically restricted to their own `dinas_inisiasi`. The redundant `dashboard.js` "own-repost-status" endpoint built in item 3's first pass was removed. Verified via curl that TAB sees everything, a PIC sees only their own, and TAB-only routes still 403 for non-TAB.

**Item 6 (REQ-RDT-NAV-09, reusable multi-value paste filter)**: built a shared `rdt-multi-value-filter` component (paste box, newline/comma split, dedupe, OR-match) mirroring the existing `pagination` shared-component pattern, wired into 5 of 6 named tables: Repost Review, Confirmation (pending), Investigation queue, Need Approval transparency, and Riwayat Repost TAB/Dinas. **Dashboard-Detailing was flagged as a pre-existing gap, not silently skipped** — it has no transaction table in the Angular app at all (only progress + comment thread), so there was nothing to attach a filter to.
