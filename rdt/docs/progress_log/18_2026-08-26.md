## Batch 3.5a — Persist: modul murni

{duplicate-check,supersede-check,original-file}.ts`. Dua yang pertama fungsi murni penuh (nol DB).

## Batch 3.5b — Persist: handler transaksi 🔴

`modules/repost/persist/{persist.controller,persist.service}.ts` — `POST persist` (upload row →
lock+`evaluateSupersede` pasangan lama → 409 kalau ada ledger/CONFIRMED → insert ter-chunk
(param-cap 65535) → simpan file original via `StorageService` → duplicate-check → comment per
`dinas_target` distinct via `PairCommentService`) + `GET uploads/:id/download` (otorisasi
inisiator/target-sekarang/target-lampau-lewat-audit-chain/TAB). Kolom insert dibatasi HANYA yang
parser Format CBO hasilkan + turunan (bukan 65 kolom kontrak lama) — `category` sengaja
ditambahkan di luar daftar literal prompt karena `ReassignmentService`/`InvestigationService` yang
sudah jalan bergantung padanya.

Diuji lewat HTTP nyata: parse+persist file TJ asli → 490 baris tepat sesuai breakdown Batch 1;
confirm 1 baris → tepat 2 ledger entry; supersede blocked (baris sudah CONFIRMED) → 409; supersede
sukses (baris masih PENDING semua) → upload lama `SUPERSEDED`, baru `ACTIVE`.

Hasil: 118→137 test / 19 suite.

`POST :batchId/subdocs` — default ke SEMUA baris `subdoc_id IS NULL` batch itu (bukan semua baris
batch), `transaction_ids` custom wajib subset dari unassigned. `GET history` — **satu-satunya**

Hasil: 161→175 test / 24 suite. **Batch 4 tuntas.**

## Batch 5b — Dashboard baca-saja (+ 1 bug nyata diperbaiki)

**Bug nyata ditemukan & diperbaiki** (bukan di `rdt/backend/`, tetap dibiarkan di sana): `kpis`'s
`waiting_to_repost` di kode lama outer-WHERE-nya memakai list status BLOCKING-only yang SAMA

SELALU balikin 0 di produksi. Diperbaiki di port Nest (outer WHERE diperluas ke union
BLOCKING+RESOLVED). Diverifikasi: sebelum fix `0`, sesudah fix `4` — persis jumlah pasangan
resolved-tapi-belum-di-subdoc nyata.

Diuji lewat HTTP nyata: reassign-chain-ke-target-asli (kartu tetap di target ORIGINAL walau sudah
resolve di target baru); visibility cutoff (100%+subdoc hilang, partial tetap tampil); 4 status
pill per-dinas-rollup semuanya direproduksi dengan dinas berbeda; breakdown-no-leak (pseudo-card
investigation dinas lain tak bocor).

## Batch 5.5b — Share Cost split (Batch 5.5 tuntas)

`modules/share-cost/`. TAB membelah SATU baris PENDING jadi beberapa baris `(dinas_target,
nominal)` — locked ke PENDING-only. Skema (`SPLIT_VOID`, `split_from_transaction_id`) sudah ada
dari migration `012_share_cost_split.sql` (Batch 0.5), tak ada migration baru. SUM dibandingkan
dalam SEN (integer) supaya tak salah floating point. Per-split `INSERT...SELECT` copy-forward
SEMUA kolom non-override, satu string SQL persis dari kode lama (bukan direkonstruksi terpisah
seperti persist 3.5b, karena prompt eksplisit minta "port PERSIS").

⚠️ **Verifikasi eksplisit** (per instruksi prompt) apakah logic comment "cari root pasangan,
reply-kalau-ada else top-level baru" identik `PairCommentService` (3c) — dibandingkan
baris-per-baris: **identik persis** → **`PairCommentService` DI-REUSE** (kandidat pertama yang
genuinely cocok, beda dari 4b & 5c yang sengaja divergen).

Diuji lewat HTTP nyata: split valid → asli `SPLIT_VOID` + 2 baris baru PENDING dengan
`split_from_transaction_id` benar; comment top-level pertama kali, lalu split KEDUA (actor beda)
membuktikan `PairCommentService` benar-benar **reply** ke root yang sama (bukan top-level baru
lagi) DAN implicit-recipient benar ter-notified kali ini (author beda, bukan self-excluded lagi);
mention dinas luar pasangan asli tak ikut notified di dua-duanya; SUM mismatch 1 sen → 400 atomik;
`per-dinas-rollup` abis split membuktikan `SPLIT_VOID` tak pernah bocor ke endpoint lain (total
count TIDAK termasuk 2 baris SPLIT_VOID).

Hasil: 238→254 test / 31 suite. **Batch 5.5 tuntas — seluruh fitur backend (rencana awal + yang
