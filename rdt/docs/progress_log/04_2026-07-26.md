# Session 04 — 2026-07-26 — TAB-only approval cleanup wrap-up, TJ parser fixes, comment threading, dashboard visibility rules

Continuation of a long-running RDT session (compacted once). ## Goals for this session
The user, working live and time-pressured ("gass langsung kerjakan semuanya tanpa nunggu apapun"), asked for a batch of 5 items:

1. Fix TJ Excel file column/row reading — it wasn't parsing as well as the TB file.
2. Routing: literal column value `"Ask TA"` should route to TAB (since TA and its sub-dinas are handled by TAB); `TMM` should route to `TM` via the GMF sub-dinas naming convention (dinas code + one trailing letter).
3. When reposting with a Keterangan/description, it should auto-post as a comment visible in Dashboard-Detailing (DT) for every affected dinas pair; when another dinas confirms, they should get a description field whose text posts as a reply to that comment.
4. A dinas pair shouldn't disappear from the dashboard the instant its own confirmation reaches 100% — it must stay visible until TAB has approved the export batch, since other dinas from the same submitter may still be pending.
5. Corp submissions should show up in TAB's "Need to Confirm" dashboard.

Later in the session, two more issues came in from live testing:
- Two file-reading screenshots showed a TJ file's numbers coming out wrong/doubled in the web vs. the source file.
- After login, selecting a platform (even when RDT is the only option) auto-navigated after ~900ms instead of waiting for an explicit click — user wanted this removed.
- A follow-up real-file test (`06. DT TJ - Jun 2026.xlsx`) surfaced a third bug: the parser silently returned 0 rows/success for a pivot-only file instead of erroring.

### 2. Repost description → auto-comment, confirmation description → threaded reply (new feature)

### 3. Dashboard visibility rule fix
- `rdt/backend/src/routes/dashboard.js`: "Need to Confirm" / dashboard entries now stay visible until the export batch is approved by TAB, rather than disappearing the instant a dinas pair's PENDING count hits zero. Addresses both item 4 (own-dinas early disappearance) and item 5 (Corp now appears in TAB's queue), using the same query path.

### 4. TJ file parsing — two real bugs found and fixed
Investigated by reading the actual sample file (`rdt/contoh_input/06. DT TJ JUN 2026 R1.xlsx`) and comparing against user screenshots.

- **Bug A — double-counting**: TJ workbooks contain a main sheet plus three "breakdown" sheets (`TJ-TE`, `TJ-TMM`, `TJ-Scrap`). Verified byte-for-byte that these are a reconciliation/breakdown *view* of rows already on the main sheet, not additional transactions (every one of TJ-TMM's 321 rows matched an amount already on the main sheet). An earlier session's fix had wrongly treated them as a second data source, so every transaction was counted twice (explains the screenshot showing TM = 797,421.97 instead of the correct 473,933.51 + duplicate 323,488.46). Fix: `rdt/backend/src/parser/excelParser.js` now skips these sheets entirely, same as any other reference/lookup sheet (removed `SECOND_FORMAT_HEADERS` / `extractSecondFormatSheet` second-source logic).
- **Bug B — wrong-column fallback**: 14 rows have both a free-text note in Remarks (e.g. "Scrap. Mohon ditakeout") *and* a real routing value in "Review TJ" (e.g. "TA"). The parser only consulted "Review TJ" when Remarks was completely empty, so these 14 rows fell into unroutable/NEEDS_REVIEW despite having a valid routing value available. Fixed in `excelParser.js` so "Review TJ" is also tried when Remarks doesn't resolve to a route.
- Verified against the file's own Summary pivot after both fixes: TM 473,933.51 / TAB 42,046.53 / TE 84.36 — exact match, no more phantom "Unknown"/wrong CORP bucket.
- `rdt/backend/test/parser.test.js` updated to reflect corrected TJ-TE/TJ-TMM/TJ-Scrap behavior (skip-sheet expectation) and the updated `mainNeedsReview` count (14 fewer rows stuck in review).
- Full `parser.test.js` suite (including the ~12.6-minute TB regression test, which just runs slowly on this machine — not a hang) passed after the fix; TB behavior unaffected.

### 5. Empty/pivot-only file now errors instead of silently succeeding
- Live-tested against `rdt/contoh_input/06. DT TJ - Jun 2026.xlsx` per user request, hitting the actual `/api/parse` endpoint (not just the parser function). This file turned out to be pivot/summary-only — a single sheet, 11 rows, rows 3–11 being literally the pivot grid (Row Labels × Ask TA/TA/TE/TMM/Grand Total), with no Account/Ref.Doc/detail transaction rows at all. There is no line-item data to extract from a pure pivot.
- Previously the backend silently returned "0 rows, success" for such a file, which read to the user as a misparse.
- Fixed in `rdt/backend/src/index.js`: the parse endpoint now returns an explicit error when zero detail rows are produced — *"File tidak mengandung baris detail transaksi yang bisa diproses... pastikan file yang diupload adalah file detail transaksi (DT), bukan file ringkasan/pivot saja."*
- Confirmed via live `curl` against the running server for both this pivot-only file (now errors clearly) and the earlier-fixed detail file (still matches pivot totals exactly).

### 6. Auto-navigate-after-login removed
